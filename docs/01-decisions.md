# 关键决策记录（为什么是这样，以及什么时候该推翻）

> `AGENTS.md` 说「怎么改」，这份说「当初为什么这么定」。
> 每条都标了「什么情况下该重开」，因为决策会过期，前提不会。

---

## D1 · 服务端推理，浏览器只播放

**背景**：四轨分离是重计算，浏览器也能跑 ONNX Runtime Web。

**选择**：推理放服务端。

**理由**：
- 浏览器端同一时刻只能用一个后端，四轨串行反而更慢；
- 模型要重新下载一遍，且进不了 HTTP 缓存之外的持久层；
- 服务端写盘即缓存，播放、下载、重试共用同一批 WAV，`/media` 静态托管天然支持 Range 请求。

**代价**：用户必须先跑一个本地服务，不能「打开网页就能用」。

**什么时候重开**：如果目标变成「零安装」，浏览器端方案（WebGPU + 量化模型）值得重新评估。

## D2 · 用 ONNX 而不是 PyTorch（**已决定推翻**）

**背景**：原生 `demucs` 依赖 PyTorch，装完 2.5 GB。

**当时的选择**：`demucs-onnx` + `onnxruntime-gpu`，包体 160 MB，一个 `uv sync` 搞定。

**当时的理由**：目标用户是「自己电脑上用」，装机体积和「不碰 CUDA 之外的依赖」优先。

**代价（事后看是决定性的）**：
- 上游 `separate()` 把分块循环封死，拿不到逐块回调 → 进度和取消只能自己重写分块算法；
- 输入形状导出时锁死 `(1,2,343980)`，块长与 batch 都改不了；
- 加音高分析时发现 FCPE 只有 PyTorch checkpoint，没有 ONNX。

**已被推翻**：下一阶段改用 PyTorch，见 `03-pytorch-dual.md`。

**教训**：包体是可以妥协的，**模型可换性不能**。选框架时要问「半年后加一个新模型要付多少成本」。

## D3 · 自己驱动 InferenceSession，不用上游 `separate()`

**背景**：`demucs_onnx.separate()` 一行就能出四轨。

**选择**：复制它的分块算法（7.8 s 定长、1/4 重叠、三角窗 overlap-add），自己写循环。

**理由**：上游把循环封在函数内部，没有回调 → 没有真实进度、不能中断。取消粒度只能到「整条 stem」（几分钟）。

**代价**：这段数值代码从此归项目维护。改完必须与上游逐采样比对（max abs diff < 1e-3），否则是静默降质。

**什么时候重开**：如果上游提供了 `on_chunk` 回调，立刻删掉我们这份。

## D4 · 默认档位是「仅人声」

**背景**：`htdemucs_ft` 是四个专家，每个专家都要完整跑一遍整曲，工作量是单专家的 4 倍。

**选择**：`DEFAULT_TIER = "vocals"`，只跑人声专家。

**理由**：抽人声是最高频的用法；四轨档仍然可选。同时 `/api/models` 要把默认档排在列表第一位，否则前端会选中首项。

**代价**：想做「伴奏」的用户要多点一次。

**什么时候重开**：如果产品定位变化，默认值应该跟着变，但**不要在 UI 里隐藏四轨档**。

## D5 · 会话不常驻，每批跑完就释放

**背景**：早期设计是「四个专家全部常驻，省掉每次 4 s 的加载」。

**选择**：每批结束 `sessions.clear()` + `runtime.release_sessions()`，下一个专家重新建图。

**理由**：单个专家跑完一个分块后，CUDA arena 会涨到约 3.2 GB 且不回缩；四个同时驻留 = 7.8 GB，8 GB 笔记本卡必然 OOM。重建约 4 s，比失败重来便宜得多。

**代价**：四轨档固定多花约 16 s。

**什么时候重开**：如果目标是 24 GB 以上的工作站卡，常驻能省 16 s，值得回报。

---

## D6 · 并行度默认 1，且是实验性开关

**背景**：参数 `parallel` 支持 1–4 个专家同时跑。

**选择**：默认 1；前端给控件但标「实验性」，文案只说「一个专家就能跑满 GPU 算力」。

**理由**：实测两个专家抢同一块 GPU，单块耗时翻倍、显存翻倍、吞吐不变；CPU 上同样是负优化（85 s → 143 s）。单 session 已经吃满设备，并发只是把同一份算力切成两半。

**代价**：保留了一个「只会让结果变差」的开关，仅用于实验。

**什么时候重开**：多卡，或者模型小到单卡跑不满（例如换成本极低的轻量模型）。

## D7 · 任务队列单 worker

**背景**：用户可能一次拖入多个文件。

**选择**：`ThreadPoolExecutor(max_workers=1)`，队列上限 3，超出直接 429。

**理由**：并发跑两个任务会让显存和内存同时翻倍，且单曲已经吃满设备；「排队但能完成」比「同时跑但都变慢」更可预期。

**代价**：批量上传时用户要等。

**什么时候重开**：如果推理下沉到子进程且显存可分区（多卡 / MPS），可以并行。

---

## D8 · 前端波形不解析为 AudioBuffer

**背景**：画波形最直接的做法是 `decodeAudioData()` 然后取峰值。

**选择**：直接解析 PCM-16 WAV 字节算峰值。

**理由**：`decodeAudioData` 会额外持有一份 float32 `AudioBuffer`，3 分钟立体声约 63 MB/轨，四轨 250 MB，只为画一张静态图。PCM-16 的原字节本来就是峰值来源。

**代价**：只适用于 16-bit PCM WAV；换格式要重写解析。本项目的输出格式固定，所以不是问题。

**什么时候重开**：如果输出改成 float32 或 mp3 直出。

---

## D9 · 视图切换用类而不是 `v-show`

**背景**：两个视图（任务列表 / 工作台）需要一个显示一个隐藏。

**选择**：`.view { display: none }` + `.view.is-active { display: block }`，用 `:class` 切换。

**理由**：`v-show` 通过移除 inline `display` 来显示，但类规则里的 `display:none` 仍然生效，结果是整块白屏。这个坑实际踩过。

**什么时候重开**：如果改用 `<RouterView>`，由路由决定挂载，这个模式自然消失。

---

## D10 · 任务状态放内存，产物落盘

**背景**：是否需要数据库。

**选择**：任务表是进程内 dict，产物写 `data/jobs/{id}/`，每小时清理 24 h 前的目录。

**理由**：单机单用户，重启后看不到历史任务是可以接受的；但**文件必须留**，因为「重试」依赖 `input.wav`，播放依赖 `stems/*.wav`。

**代价**：`--reload` 会清空任务表；进程崩溃后磁盘上会留孤儿目录（靠 TTL 清理兜底）。

**什么时候重开**：多用户或需要历史记录时，至少要用 SQLite。
