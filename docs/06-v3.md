## 1. 已定下的约束

| # | 约束 | 依据 |
|---|---|---|
| 1 | **导出层不做平滑**（`smooth = 1`），平滑交给 OpenUtau / DAW | D17：3 帧中值滤波就把相邻帧差抹掉 26%，9 帧抹 83%，不可逆 |
| 2 | 曲线控制点密度 50 ms → **25 ms**（≈ `UCurve.interval` 的 5 tick） | D17：50 ms 下颤音一个周期只剩 3–4 个点，看着就是「平」 |

| 4 | 音高分析是**独立功能**，不与分轨耦合 | 本次拆分（`scope`）的核心 |

## 2. 验收手段要先于模型（V2 真正的瓶颈）——已有 vocadito 基线

V2 的指标原本都是「和 OpenUtau 的 GAME 输出比」，等于用同一模型的后代做尺子。
2026-10-30 引入 **vocadito**（40 段独唱、人工标注音符、每首两个标注者）后，第一次有了绝对口径：

```powershell
uv run python scripts/eval_vocadito.py                       # 全量 40 首，medium + 默认参数
uv run python scripts/eval_vocadito.py --seg 0.1 --est 0.15   # 换参数重测（约 60 s）
```

**基线（40 首均值）**：

| | 音符数 | 起音召回 | 起音精确 | F1 | 音高一致 |
|---|---|---|---|---|---|
| GAME medium（默认参数） | 48 | 74.1% | 81.4% | 0.776 | 82.6% |
| 人类 A2 vs A1 | 47 | 80.1% | 90.1% | **0.848** | 87.7% |

**模型内部旋钮基本无收益**（est 0.1–0.2、seg 0.10–0.20、半径 0.01–0.02、nsteps 8/16、t0 0/0.1/0.25、
medium/large 共 13 组）：F1 全落在 0.771–0.782，只有 large 明显更差（0.771）。

**但切片参数是例外，而且有效**——切片阈值决定每段喂给模型的上下文，之前从没扫过：

| 切片阈值 | 音符数 | 起音召回 | 起音精确 | F1 | 音高一致 |
|---|---|---|---|---|---|
| −30 dB | 41 | 64.0% | 81.9% | 0.652 | 68.6% |
| −40 dB（现行默认） | 48 | 74.1% | 81.4% | 0.776 | 82.6% |
| −50 dB | 48 | 75.0% | 81.6% | 0.782 | 83.8% |
| −60 dB | 48 | 74.7% | 82.1% | 0.781 | 84.6% |
| **−70 dB** | 48 | **75.2%** | **82.5%** | **0.787** | **84.9%** |
| −70 dB + seg 0.15 | 49 | 75.7% | 81.0% | 0.782 | 84.8% |

结论修正：**`-40` 切得太碎，`-70` 让音高 +2.3 点、F1 +1.1 点**，仍差人类天花板 6 个点。
`-30` 会直接把长音切断（音高掉到 68.6%），说明这个参数不是「越小越好」，是「别把连续音切碎」。

**上生产前必须先解决内存**：阈值越宽 → 切片越长 → segmenter 的 O(T²) 越危险
（188 s 整段实测要 5.6 GB）。要做的是「−60 dB + 单片最大长度上限（如 30 s）」，
而不是直接放开阈值。

**切片长度的风险（上生产的前提）**：阈值越宽切片越长，而 segmenter 注意力是 O(T²)。
188 s 素材实测：`-40` 最长片 45.8 s、`-60` 51.2 s、`-70` 62.0 s；整段 188 s 不切时会要 5.6 GB 直接 OOM。
**连续演唱的长歌在任何阈值下都可能出现超长片**，所以除了阈值，单片长度必须有硬上限。

**已在 V2 落地（2026-10-30）**：`config.GAME_SLICE_THRESHOLD_DB = -60`、`GAME_MAX_SLICE_SEC = 30`，
worker 里用 `_CappedSlicer` 包住上游 Slicer，超长片在**能量最低处**再切（固定时长切会把长音劈开）。
两边数据集上的取舍：

| 切片阈值 | vocadito（人类标注，F1 / 音高） | 科学MIMI（GAME 参考，召回 / 精确 / 音高） |
|---|---|---|
| −40（上游默认） | 0.776 / 82.6% | 98.7% / 97.8% / 97.1% |
| −50 | 0.782 / 83.8% | 98.7% / 97.9% / 96.5% |
| **−60（现默认）** | 0.781 / **84.6%** | 97.7% / 98.3% / 96.9% |
| −70 | **0.787 / 84.9%** | 98.8% / 98.3% / 96.4% |

歌曲级参考上四个阈值都在噪声内（96.4–97.1%），人类标注上宽切片一致更好 → 取 −60。
不取 −70 是因为收益只剩 +0.3 点，而切片长度进一步变长、OOM 风险更高。

**试过但不成立的方向**：

| 尝试 | 结果 |
|---|---|
| `t0` 0.1 / 0.25 | 47 音符、F1 与 t0=0 无差异（边界最终收敛） |
| `nsteps` 16 | F1 0.778，与 8 没有区别，白花一倍时间 |
| `large` 体积 | F1 0.771，人工标注上同样更差 |
| **谱通量起音融合**（把 `onset.json` 的峰插进 GAME 音符内部） | z=2.0：召回 75.2→77.7%，但精确 82.5→71.3%，**F1 0.784→0.740**；z=3.5 → 0.772；z=5.0 → 0.781，全不如不融合 |

融合失败的原因值得记住：谱通量峰落在**辅音**上，比人类标注的音符起点（元音起振）早 10–30 ms，
而且同一音符内常有多个能量峰。要能用，得要求「能量谷 + 音高重新起振」同时成立，
那是新算法，不是加个开关。

**帧级分解（`scripts/eval_f0.py`，vocadito 人工 F0，49 万帧）**：

| 指标 | 值 | 含义 |
|---|---|---|
| RPA（±50 音分） | **98.7%** | 曲线本身极准 |
| RCA（忽略八度） | 98.8% | 八度错不是主要问题 |
| 八度错（1200±100 音分） | **0.1%** | 单声部模型在清唱上几乎不跳八度 |
| 有声召回 / 精确 | 99.9% / 85.4% | 该有声的都找到了；我们报的有声里 15% 是假的（背景噪声） |

**结论：音高曲线不是瓶颈，边界与「有声判定」才是。** 同一组 GAME 边界下换音高来源（20 ms 逐点口径）：

| 音高来源 | 一致率 |
|---|---|
| GAME estimator | 81.5% |
| **FCPE 段内中位数** | **82.8%** |

所以在人工标注上，FCPE 的中位数比 GAME 的 estimator 还准 1.3 个点——这反过来说明
当初在 `科学MIMI` 上「GAME 更好」的结论是**参考偏向**造成的（那份参考的音高就是 GAME 给的）。
V3 若要重选音高来源，应先做人工标注对照，不要沿用那条结论。

**多种子集成（D3PM t0=0 vs 0.15）**：

| 方案 | 音符 | 召回 | 精确 | F1 | 音高 |
|---|---|---|---|---|---|
| 种子 1 | 47.7 | 74.7% | 82.1% | 0.7795 | 84.6% |
| 种子 2 | 47.1 | 74.0% | 82.5% | 0.7781 | 84.3% |
| 取交集 | 45.9 | 73.0% | 83.3% | 0.7755 | 82.0% |
| 取并集 | 49.0 | 75.6% | 81.3% | 0.7806 | 84.6% |

并集只高 0.0011，代价是 2× 推理时间 → **不采用**。

剩余未试：
- **固定 30 s 分块 vs 静音切片**：既解决 OOM，也能验证「上下文更长更好」是否被分块破坏。
- **安静段的发声判定**：`科学MIMI` 60–70 s（−25 dBFS，比平均低 8 dB）有声比例只有 17%，
  错误率 34.8%；而 70–80 s / 140–150 s 是纯静音（−80 dBFS）→ 0% 有声是对的。
  安静段的「该有声/没声」需要单独的阈值策略，现在是一刀切。

## 3. 待重构项（按痛感排序）

1. **导出参数散落**：`smooth` 在 `schemas.ExportParams`，`bpm=120` 写死在 `render_export` 默认值，
   曲线密度在 `domain/ustx.py` 的 `DENSITY_SEC`，`PITD_MAX_DEVIATION` 又是另一个常量。
   → 收敛成一个 `ExportSettings`，由创建参数带下来。
2. **`features/` 目录语义膨胀**：`pitch.json` / `onset.json` / `notes.json`（导出输出）/ `notes_game.json`
   四个文件，谁是输入谁是输出只能看代码。→ 引入 `features/index.json` 或严格的 `inputs/` 与 `derived/` 分层。
3. **前端 `App.vue` 三合一**：轮询、视图切换、任务创建都在一个文件里，
   拆成 `composables/useJobs`（轮询 + 列表）与 `useCreateJob`（弹窗 + 参数）。
4. **参数校验两头各写一遍**：pydantic 模型在 `app/schemas.py`，表单在 `CreateJobDialog.vue`，
   默认值与取值范围重复。→ 由 `/api/params/schema` 输出，前端据此生成。
5. **旧格式兼容代码该删**：`config.scope_from_meta` 里的 `_LEGACY_MODE_TO_SCOPE`、
   `Job.mode` 的残留判断，等 `data/jobs` 清空后一并移除。
6. **`orchestrator` 的进度 band 是手写常量**（0.05/0.67/0.73/0.13…），加阶段就得重排。
   → 把每个 stage 的权重写进配置，按存在与否归一化。
7. **缺集成测试**：`pytest` 只覆盖纯函数与 API 形状，`orchestrator` 的真实调度没有测试，
   因为素材不能进 CI。→ 造 1 s 的合成 wav fixture，跑一次「只分析」全链路。
8. **依赖分层**：torch/lightning 都在主环境，但 GAME 只在子进程用。
   → 若走 ONNX（D16 已否决，可复议），主进程这一侧能彻底瘦下来。

## 5. V3 技术方案（2026-10-30 确认）

方向以根目录 `V3 构想.md` 为准，本节只写落地细节、风险与待办。

### 5.1 运行时与模型

| 模型 | 形态 | 体积 | 来源 | 备注 |
|---|---|---|---|---|
| demucs（htdemucs_ft 四专家） | ONNX | 约 160 MB | v1 用的 `demucs-onnx==0.3.4` | **不重新导出**；但上游 API 没有逐块回调，v1 已重写分块循环（7.8 s 定长、1/4 重叠、三角窗 overlap-add），这段数值代码要搬过来 |
| GAME | ONNX | 190 MB（只留 medium） | 上游 release `GAME-1.0.3-medium-onnx.zip` | 需要静音切片 + 单片段长度上限（v2 已验证 O(T²) 会 OOM） |
| FCPE | ONNX | 约 20 MB | **需要从 v2 的 PyTorch checkpoint 一次性导出** | 导出后必须做数值等价验收：与 PyTorch 逐帧 f0 比对 |
| 主旋律/和声分离（候选） | ONNX | 50–500 MB | 待选型，需先确认许可 | 见 5.4 |

运行时：`onnxruntime-directml`（GPU）+ CPU 兜底，二选一装（同模块名不能共存，v1 已踩过）。
**注意**：`docs/perf-audit.md` 记录 `onnxruntime-directml` 最新只到 **1.24.4**，比主线落后 7 个版本，
GAME 的图能否在这个版本上跑通必须先 spike。

### 5.2 流水线与数据契约

产品形态（前端驱动）：
1. 上传 → 解码 → 分轨（主任务，必跑）
2. 四条音轨；**展开某条音轨**才计算该轨的音高（挂载在预览上，与播放头同步）
3. 人声轨展开时可**手动触发**音符提取 → 音高线上层叠加半透明音符条
4. 音符完成后**单独触发导出**（MIDI / USTX）

后端契约允许重构，但建议保留两条既有边界（它们是「换模型不动业务层」的落点）：
- 推理在子进程，父进程只读事件流（v2 的 `python -m app.worker <stage>` + stdout JSON）
- 产物按 `data/jobs/{id}/` 分目录，参数快照进 `meta.json`（v2 的 scope/params/parent 模型可复用）

### 5.3 与 v2 的既定约束的衔接

| v2 决策 | V3 处理 |
|---|---|
| D17：导出不做中值平滑，控制点密度 50 ms → 25 ms | **保留**。注意 10 ms 是分析帧率（pitch.json），25 ms 是 USTX 控制点间距（`UCurve.interval` 5 tick ≈ 26 ms），两者别混 |
| D18：v2 的调参结论全部作废 | 保留；V3 不继承任何默认参数，重新以盲听确定 |
| D14：参数在创建时定稿 | 保留（音高与音符都是派生，参数随请求走） |

### 5.4 扩展功能

**主旋律/和声分离**：音轨栏上的手动按钮，拆出「主旋律人声 / 和声」两栏，两栏与原人声轨同性质
（可再次拆，但没有意义，UI 上应禁止）。两栏都能提音高与音符，默认推荐主旋律。
选型需要满足：ONNX 可跑、许可允许分发、单次 3 分钟歌的增量耗时 < 30 s。

**变速不变调分析（实验）**：对音源做相位声码器慢放（0.8×）→ 分析 → 时间映射回原速。
已知代价：相位声码器会抹瞬态，而瞬态是边界检测的主要证据；且边界误差在还原时会按比例放大（0.8× → ×1.25）。
**必须用盲听判断**，不能只看指标。

### 5.5 待办与风险

1. **spike（P0）**：`onnxruntime-directml` 1.24.4 上跑 demucs / GAME / FCPE 三张图，记录算子回落与速度；
   不通过则退回「CUDA EP + CPU 兜底」或「全 CPU」。
2. **FCPE 导出的等价性**：导出后对 vocadito 40 首做帧级 RPA 对比（v2 已建好 `scripts/eval_f0.py`），差 ≤0.1 点才算等价。
3. **权重分发**：首次下载合计约 400 MB（demucs 160 + GAME 190 + FCPE 20 + 提纯模型），
   需要统一下载器 + 断点续传 + 体积提示；开源发布前逐个确认许可。
4. **drums 的音高预览**：打击乐没有稳定基频，直接画音高线是噪声，需要「无音高」判定或改用能量包络。
5. **性能目标**（待定数字，参考 v1 的 perf-audit）：3 分钟歌端到端 ≤ 60 s，峰值显存 ≤ 2 GB，展开音高 ≤ 1 s 出图。
6. **仓库形态**：V3 是新仓库 / 同仓库新目录 + 分支，需要确认；`V3 构想 copy.md` 是重复文件，建议删。

### 5.6 调研结果：运行时与权重的现状（2026-10-30 联网核实）

**① 7.8 s 不是随手写的数值，是模型的硬约束。**
`htdemucs` 训练时的最大分段就是 7.8 s，demucs 源码里对 `--segment > 7.8` 会直接报错；
2026 年的 ONNX 导出（HF `StemSplitio/htdemucs-onnx`）把输入固定成 `(1, 2, 343980)`
—— 343980 = 7.8 s × 44100。也就是说**分块循环是图本身的要求**，不是 v1 的临时决定：

- `7.8 s 定长`：模型训练段长，图输入写死
- `1/4 重叠 + 三角窗`：demucs 的 `overlap=0.25`、`transition_power=1` 默认值，用于消除接缝
- 上游 `demucs_onnx.separate()` 确实存在，但把分块循环封在内部，**没有逐块回调**，
  所以进度与取消只能自己驱动 `InferenceSession`（v1 就是这么做的）

**② demucs 的 ONNX 现状（比 v1 那年好）**

| 方案 | 说明 | 取舍 |
|---|---|---|
| `demucs-onnx==0.3.4`（v1 用的） | htdemucs_ft 四专家，需自己驱动分块 | 质量最好（FT），约 4× 计算量 |
| HF `StemSplitio/htdemucs-onnx` | 单文件 4 轨，输入固定 7.8 s，四轨都是真实预测 | 省 3–4× 时间，但**不是 FT**，SDR 略低 |
| 自行导出 htdemucs_ft | 2026 有公开的导出方案 + parity 工具（316 MB、opset 17，STFT roundtrip 5e-6） | 可控，但要自己维护导出与等价性测试 |

**③ DirectML EP 确实落后主线**（与 `docs/perf-audit.md` 一致，已核实）：
`onnxruntime-directml` 最新 1.24.4（2026-03 发布），而主线 ONNX Runtime 已到 1.31.x。
GAME 的图能否在 1.24.4 上跑通、算子回落多少，仍是 spike 的头号未知数。

**④ 更值得考虑的路：Windows ML（新版）**
微软现在把 **WinML 作为 Windows 上跑 ONNX 的推荐路径**：系统自带共享的 ONNX Runtime，
按硬件自动下载厂商 EP（CPU 与 DirectML 在盒内，CUDA/NPU 按需拉取）。
这正好对应「CPU 兜底 + 可选 DML / CUDA 加速」的目标，且应用不必自带运行时。
**但它面向 WinRT / .NET / C++（NuGet + Windows App SDK），Python 里不能直接用。**
所以这是一条真正的架构岔路：V3 如果继续 Python（FastAPI + 本地 Web UI），就只能走
`onnxruntime-directml 1.24.4` 或 `onnxruntime-gpu`；如果愿意把推理层做成原生，
WinML 才是「面众 + 免装运行时」的正解。

**⑤ FCPE 确实没有官方 ONNX**：上游仓库与 HF 都只有 PyTorch checkpoint（另有一个 Burn 格式的
第三方导出，不是 ONNX），所以「在 v2 侧用 PyTorch 一次性导出」是唯一路径，导出后必须做帧级等价验收。
